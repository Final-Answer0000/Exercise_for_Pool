# Laravelインターン課題 受験者向け評価基準

- 対象課題: [explanation.md](./explanation.md)
- 文書更新日: 2026-08-10
- 基礎点: 100点

本書では、受験者へ事前に公開する合格条件と評価観点を示します。具体的な攻撃文字列、採点時の入力値、採点記録など、採点者向けの内部手順は含みません。ただし、課題文と本書に記載していない機能を、後から必須要件として扱うことはありません。

## 1. 判定方法

次の両方を満たした場合に合格とします。

1. 100点満点中80点以上を取得する
2. 「2. 必須合格条件」をすべて満たす

点数だけで、認証回避、認可回避、保存型XSSなどの重大な問題を相殺することはできません。

| 判定 | 基準 |
| --- | --- |
| 合格 | 80点以上、かつ必須合格条件をすべて満たす |
| 再提出 | 65点以上79点以下、または修正可能な必須条件の不足がある |
| 不合格 | 64点以下、採点不能、重大なセキュリティ問題、要件と異なる技術構成 |

再提出の可否と修正期限は、募集時の運用ルールおよび提出状況を踏まえて課題担当者が決定します。

## 2. 必須合格条件

次の7項目は足切り条件です。1つでも満たさない場合、その時点の提出物は合格になりません。

### M1. クリーンな環境から再現できる

- 新しくcloneした状態から、READMEの手順だけで構築できる
- Dockerイメージのビルド、コンテナ起動、Migration、フロントエンドビルドを実行できる
- ブラウザからアプリケーションへアクセスできる
- 既存の`vendor`、`node_modules`、Dockerボリューム、ホスト固有設定へ依存しない

### M2. 指定技術を使用している

- Laravel 13.x、PHP 8.3以上、MySQL 8.x
- Laravel公式Reactスターターキット
- React 19、TypeScript、Inertia.js 3
- Laravel組み込み認証とFortify
- Docker Compose v2
- Laravel Sailを使用しない独自Docker Compose構成
- 受験者自身が管理する`Dockerfile`と`compose.yaml`

主要画面をBladeだけで実装する、WorkOSなど別の認証基盤へ置き換える、Laravel Sailを使用するなど、課題文と異なる技術構成は条件未達です。

### M3. 認証とTOTP二段階認証が一連の操作として動く

- ユーザー登録、ログイン、ログアウトが動く
- 二段階認証を有効化し、TOTPコードで確認できる
- 二段階認証を有効にしたユーザーは、ログイン時にチャレンジを要求される
- 正しいTOTPコードでログインでき、誤ったコードではログインできない
- 未使用のリカバリーコードでログインできる
- 使用済みリカバリーコードを再利用できない
- 二段階認証を無効化できる

画面やスターターキットのコードが存在するだけでなく、実際の一連の操作が成功する必要があります。

### M4. 投稿の所有者認可がサーバー側で機能する

- 投稿作成時の所有者がログインユーザーになる
- 投稿者本人だけが編集、更新、削除できる
- 別ユーザーがURLやHTTPリクエストを直接操作しても`403`になる
- 認可に失敗した場合、投稿データが変更されない
- PostPolicyなどLaravelの認可機能を使用している

React側でボタンを非表示にするだけでは条件を満たしません。

### M5. 保存型XSSが発生しない

- 投稿本文をプレーンテキストとして描画する
- `script`タグやイベント属性などを含む投稿でもJavaScriptが実行されない
- 未加工の投稿本文を`dangerouslySetInnerHTML`などでHTMLとして描画しない

投稿を閲覧しただけでJavaScriptが実行される場合は条件未達です。

### M6. 全テストが成功する

- `php artisan test`でフィルターを指定せず全テストを実行できる
- 全テストが成功する
- テスト用データベースが開発用データやテスト実行順へ依存しない
- 認証、二段階認証、投稿認可、バリデーションの必須テストがある

テストを実行できない、失敗する、または初期生成されたExampleTestしかない場合は条件未達です。

### M7. 秘密情報をGitへ登録していない

- `.env`をGitへ登録していない
- 実在するパスワード、APIキー、トークン、秘密鍵を登録していない
- 二段階認証の秘密情報やリカバリーコードをログ、画像、提出物へ保存していない

秘密情報がコミット履歴へ含まれた場合、現在のファイルから削除するだけでは解消になりません。

## 3. 配点

| 評価項目 | 点数 | 主な評価内容 |
| --- | ---: | --- |
| A. Docker・再現性 | 10 | 指定バージョン、独自Compose構成、クリーンビルド、環境依存の排除 |
| B. Laravel設計・データベース | 10 | Migration、制約、Eloquent、Controller、Form Request、Policy |
| C. React・Inertia.js | 10 | React・TypeScript実装、フォーム状態、操作性、コンソールエラー |
| D. 認証・二段階認証 | 20 | 基本認証、TOTP、ログインチャレンジ、リカバリーコード、安全な秘密情報管理 |
| E. 投稿CRUD・認可 | 20 | 一覧、詳細、作成、編集、削除、所有者設定、サーバー側認可 |
| F. バリデーション・セキュリティ | 10 | 入力検証、入力復元、XSS・CSRF・マスアサインメント対策 |
| G. 自動テスト | 15 | 独立して再実行できる認証、2FA、CRUD、認可、異常系テスト |
| H. README・リポジトリ品質 | 5 | 再現可能な手順、Git管理対象、コミット、ブランチ、Pull Request、提出状態 |
| 合計 | 100 | |

発展機能の数よりも、必須要件を正確に実装し、テストとREADMEを含めて第三者が確認できる状態へ仕上げることを重視します。

## 4. 評価観点

### A. Docker・再現性

独自の`Dockerfile`と`compose.yaml`を理解して構成し、ホストへPHP、Composer、Node.js、MySQLを直接導入しなくても再現できるかを確認します。ポート変更、サービスの起動順、不要なDB公開、固定`container_name`の有無も評価対象です。

### B. Laravel設計・データベース

データベース制約とEloquentリレーションが要件に一致し、Resource Controller、Resource Route、Route Model Binding、Form Request、Policyなどへ責務を適切に分けているかを確認します。

### C. React・Inertia.js

主要画面がTypeScriptのReactコンポーネントとして実装され、Inertia.jsによるデータ受け渡し、入力保持、項目別エラー、送信状態、画面遷移が一貫しているかを確認します。主要操作を妨げる表示崩れやブラウザコンソールエラーも減点対象です。

### D. 認証・二段階認証

登録からログアウトまでの基本認証に加え、TOTP二段階認証の有効化、確認、ログインチャレンジ、リカバリーコード、無効化が一連の操作として安全に機能するかを確認します。

### E. 投稿CRUD・認可

CRUDが要件どおり動作し、投稿所有者がサーバー側で正しく設定されるかを確認します。別ユーザーによる画面操作だけでなく、URLやHTTPリクエストを直接変更した場合にもPolicyで拒否される必要があります。

### F. バリデーション・セキュリティ

サーバー側バリデーション、項目別エラー、入力値の復元、CSRF対策、マスアサインメント対策、保存型XSS対策を確認します。クライアント側の`required`属性やボタン非表示だけでは、サーバー側対策の代わりになりません。

### G. 自動テスト

正常系だけでなく、未認証、別ユーザー、不正なTOTP、リカバリーコード再利用、必須項目、最大文字数超過、危険な投稿本文などの異常系を自動判定できるかを確認します。

### H. README・リポジトリ品質

採点者がREADMEだけで構築・操作・テストでき、記載内容が実装と一致しているかを確認します。`composer.lock`、`package-lock.json`、`.env.example`は登録し、`vendor`、`node_modules`、ログ、秘密情報は登録しないでください。

コミットメッセージが`{prefix}: {修正内容}`の形式で、修正内容が日本語で具体的に記載されていること、主要な作業単位でブランチを分けていること、Pull Requestに変更内容とテスト結果を記載して`main`へマージしていることも評価します。細かなブランチ名の違いだけで必須合格条件の未達にはしませんが、すべてを`main`へ直接コミットした場合や、変更理由を追えない履歴は減点対象です。

## 5. 採点時の確認方法

採点者は、原則として次の方法で確認します。

1. 共有されたコミットを新しいディレクトリへcloneする
2. READMEの手順だけでDocker環境をビルド・起動する
3. Migration、Seeder、フロントエンドビルドを実行する
4. `php artisan test`で全テストを実行する
5. ブラウザで認証、二段階認証、投稿CRUD、認可、バリデーションを操作する
6. ブラウザコンソール、Git管理対象、コミット・Pull Request履歴、依存パッケージのaudit結果を確認する

課題文に記載された要件を検証するため、提出物に記載されていない入力値や操作順で確認する場合があります。これは隠れた追加要件ではなく、正常系・異常系の両方で要件が成立するかを確認するためのものです。

## 6. 提出前チェック

- READMEを見ながら新しいcloneと空のDockerボリュームから構築した
- `docker compose up -d --build`が成功した
- MigrationとSeederが成功した
- `npm run build`がコンテナ内で成功した
- `php artisan test`がフィルターなしで全件成功した
- 二段階認証を実際の認証アプリで確認した
- 別ユーザーによる編集、更新、削除が`403`になることを確認した
- 危険な投稿本文を保存してもJavaScriptが実行されないことを確認した
- 主要画面でブラウザコンソールエラーがないことを確認した
- READMEと実装のURL、コマンド、画面遷移が一致している
- 主要な作業をブランチとPull Requestに分け、変更内容とテスト結果を記載した
- 提出対象が`main`へマージされ、提出するコミットハッシュを確認した
- Git管理対象とコミット履歴に秘密情報がないことを確認した
