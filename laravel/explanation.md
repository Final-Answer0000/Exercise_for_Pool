# Laravelインターン課題

## 認証付きブログアプリケーション

- 文書更新日: 2026-08-10
- 対象バージョン: Laravel 13.x
- 受験者向け評価基準: [evaluation.md](./evaluation.md)

## 運用事項

### 提出期限

提出期限は、原則としてオリエンテーション実施日の1か月後です。具体的な提出日時は課題担当者から通知します。

期限までにすべての要件を満たすことが難しいと判断した場合は、期限を過ぎてからではなく、判明した時点で進捗、未完了項目、原因、完了見込みを課題担当者へ共有してください。

### Slack DMでの提出方法

課題担当者のSlack DMへ、次の内容を共有してください。

- GitHubリポジトリURL
- 採点対象のブランチ名
- 採点対象のコミットハッシュ
- READMEに従ってクリーンな環境から実行した結果
- `npm run build`の実行結果
- `php artisan test`による全テストの実行結果
- 既知の問題または未実装項目

提出後に追加コミットを行った場合は、採点対象が変わったことと新しいコミットハッシュを改めて共有してください。採点者は共有されたコミットを基準に確認します。

### 合格後の面談

提出物が[受験者向け評価基準](./evaluation.md)を満たした場合、課題後面談を実施します。

面談では、実装内容、設計判断、認証と認可の違い、二段階認証の処理、テスト方法、発生した問題とその解決過程について確認します。アプリケーションが動作することだけでなく、自分の実装について説明できるようにしてください。

### リポジトリの公開範囲

提出リポジトリは原則として最初からPrivateで作成し、課題担当者をCollaboratorとして招待してください。Publicで提出するよう個別に指示された場合を除き、他の受験者が解答を閲覧できる状態にしないでください。

Publicでの提出を個別に認められた場合も、`.env`、パスワード、APIキー、トークン、二段階認証の秘密情報などを登録してはいけません。採点と課題後面談が完了した後は、リポジトリをPrivateへ変更してください。

### IT総合基礎の扱い

IT総合基礎課題は、Laravel課題の点数および合否判定には含めません。

ただし、Git、Linux、HTTP、データベース、SQL、Docker、Webセキュリティの基礎知識は、本課題へ取り組むための前提知識です。必要な内容を確認したうえで課題へ取り組んでください。

## 1. 課題の目的

LaravelとReactを用いて、ユーザー認証と二段階認証を備えたブログアプリケーションを開発してください。

本課題では、画面が表示されてCRUD操作ができることだけでなく、次の能力を確認します。

- Laravelのルーティング、Controller、Eloquent、Migrationを適切に扱えること
- React、TypeScript、Inertia.jsを用いてフォームと画面状態を実装できること
- 認証と認可の違いを理解し、サーバー側でアクセスを制御できること
- バリデーション、CSRF、XSSなどの基本的なセキュリティ対策を実装できること
- 正常系と異常系を自動テストで検証できること
- DockerとREADMEだけで、第三者が同じ環境を再現できること
- 要件、実装、テスト結果を整理して報告できること

## 2. 指定技術

次の構成を使用してください。

| 項目 | 指定 |
| --- | --- |
| Backend | Laravel 13.x |
| PHP | 8.3以上 |
| Frontend | Laravel公式Reactスターターキット |
| UI | React 19、TypeScript |
| Laravel連携 | Inertia.js 3 |
| 認証 | Laravel組み込み認証、Laravel Fortify |
| 二段階認証 | TOTP方式 |
| Database | MySQL 8.x |
| Nodeパッケージ管理 | npm |
| 開発環境 | 独自Docker Compose構成（Docker Compose v2、Laravel Sail不使用） |
| テスト | PestまたはPHPUnit |

`composer.json`ではLaravel 13.xを対象にしてください。依存関係は`composer.lock`および`package-lock.json`で固定してください。

認証にはLaravel公式Reactスターターキットの組み込み認証を使用してください。WorkOS AuthKit、外部の認証代行サービス、SMS認証は本課題では使用しません。

公式スターターキットにはFortifyが含まれています。Fortifyを重複して導入せず、生成された構成と公式ドキュメントを確認して利用してください。

TOTPの生成アルゴリズムや暗号処理を独自実装する必要はありません。Fortifyが提供する機能を正しく設定し、React画面、認可、テストと統合してください。

## 3. 作成するアプリケーション

ユーザーが登録・ログインし、自分の投稿を作成、編集、削除できるブログアプリケーションを作成します。

未ログイン利用者も、投稿一覧と投稿詳細を閲覧できるものとします。

### 3.1 必須画面

- 投稿一覧
- 投稿詳細
- 投稿作成
- 投稿編集
- ユーザー登録
- ログイン
- 二段階認証チャレンジ
- アカウント設定
- 二段階認証設定

主要なアプリケーション画面はReact、TypeScript、Inertia.jsで実装してください。ブログ機能をBladeだけで実装してはいけません。

### 3.2 URL・HTTPメソッド

ブログ機能にはResource Controller、Resource Route、暗黙のRoute Model Bindingを使用してください。

| メソッド | URL | 公開範囲 | 用途 |
| --- | --- | --- | --- |
| GET | `/posts` | 公開 | 投稿一覧 |
| GET | `/posts/{post}` | 公開 | 投稿詳細 |
| GET | `/posts/create` | ログイン必須 | 投稿作成画面 |
| POST | `/posts` | ログイン必須 | 投稿保存 |
| GET | `/posts/{post}/edit` | 投稿者本人 | 投稿編集画面 |
| PUTまたはPATCH | `/posts/{post}` | 投稿者本人 | 投稿更新 |
| DELETE | `/posts/{post}` | 投稿者本人 | 投稿削除 |

認証と二段階認証のURLは、Fortifyおよび公式スターターキットが提供する標準ルートを使用してください。

## 4. データベース要件

### 4.1 usersテーブル

Laravel公式スターターキットが生成するユーザー情報と二段階認証用の構成を使用してください。

パスワードを画面、ログ、Inertia props、APIレスポンスへ平文で露出させてはいけません。二段階認証のセットアップキーとリカバリーコードは、本人がパスワードを再確認した設定画面で必要なときに限って表示し、通常画面の共有props、ログ、URLなどへ常時露出させないでください。

### 4.2 postsテーブル

最低限、次のカラムを持たせてください。

| カラム | 要件 |
| --- | --- |
| id | 主キー |
| user_id | users.idへの外部キー、必須 |
| title | VARCHAR(255)、必須 |
| content | TEXT、必須 |
| created_at | 必須 |
| updated_at | 必須 |

ユーザーを削除できる構成を残す場合は、そのユーザーに属する投稿をどう扱うかをMigrationで明示してください。

### 4.3 Eloquentリレーション

次のリレーションを定義してください。

- Userは複数のPostを持つ
- Postは1人のUserに属する

Migration、Factory、Seederを用意し、SQLを手作業で実行しなくても初期データを作成できるようにしてください。

## 5. ブログ機能

### 5.1 投稿一覧

- 未ログインでも閲覧できる
- 新しい投稿を先に表示する
- 投稿者名、タイトル、投稿日時を表示する
- 1ページ10件でページネーションする
- 投稿詳細へ移動できる

### 5.2 投稿詳細

- 未ログインでも閲覧できる
- タイトル、本文、投稿者名、投稿日時、更新日時を表示する
- 投稿者本人にだけ編集・削除操作を表示する
- 本文中の改行を保ったまま、プレーンテキストとして表示する

### 5.3 投稿作成

- ログイン済みユーザーだけが利用できる
- タイトルと本文を入力できる
- 保存した投稿の`user_id`は、リクエスト値ではなくログインユーザーから設定する
- 正常に保存した後、利用者が結果を確認できる画面へ遷移し、成功メッセージを表示する

### 5.4 投稿編集

- 投稿者本人だけが利用できる
- 現在の値を初期表示する
- バリデーション失敗時は、送信直前の入力内容を保持する
- 正常に更新した後、利用者が結果を確認できる画面へ遷移し、成功メッセージを表示する

### 5.5 投稿削除

- 投稿者本人だけが実行できる
- HTTPの`DELETE`メソッドを使用する
- 実行前に確認操作を設ける
- 削除後は投稿一覧へ遷移し、成功メッセージを表示する

## 6. 認証要件

最低限、次の機能を正常に利用できるようにしてください。

- ユーザー登録
- ログイン
- ログアウト
- ログイン状態に応じたナビゲーション表示
- 認証が必要な画面への`auth`ミドルウェア適用
- ログイン試行に対するFortifyのレート制限
- セッションを利用したブラウザ認証

未ログイン利用者が投稿作成・編集・削除へ直接アクセスした場合、ログイン画面へ遷移し、データを変更してはいけません。

## 7. 二段階認証要件

FortifyのTOTP方式を使用し、次の一連の操作を実装してください。

### 7.1 有効化

- ログイン済みユーザーがアカウント設定から有効化できる
- 設定変更前にパスワード再確認を求める
- QRコードを表示する
- QRコードを利用できない場合のセットアップキーを表示する
- 認証アプリが生成した6桁コードを入力して設定を確認する
- 有効化操作を開始しただけでは有効扱いにせず、正しいコードによる確認後に有効化する
- 有効化完了を画面上で確認できる

### 7.2 ログイン時の認証

- 二段階認証が有効なユーザーは、メールアドレスとパスワードの認証後に二段階認証チャレンジへ遷移する
- 正しいTOTPコードを入力するとログインが完了する
- 誤ったコードではログインできず、エラーを表示する
- 二段階認証完了前に、認証必須画面へアクセスできない

### 7.3 リカバリーコード

- 有効化後にリカバリーコードを確認できる
- リカバリーコードを再生成できる
- 未使用のリカバリーコードでログインできる
- 使用済みのリカバリーコードを再利用できない
- リカバリーコードをURL、ログ、通常のInertia propsへ露出させない

### 7.4 無効化

- ログイン済みユーザーが無効化できる
- 無効化前にパスワード再確認を求める
- 無効化後は通常のログインフローへ戻る

## 8. 認可要件

認証済みであることと、対象の投稿を操作できることは別々に判定してください。

- PostPolicyを作成する
- 投稿者本人だけが自分の投稿を編集・更新・削除できる
- 別ユーザーが編集・更新・削除を直接リクエストした場合は`403 Forbidden`を返す
- 認可失敗時にデータを変更しない
- React側でボタンを非表示にするだけで済ませず、Laravel側でも必ず認可する

## 9. バリデーション要件

作成と更新のバリデーションにはForm Requestを使用してください。

| 項目 | ルール |
| --- | --- |
| title | required、string、最大255文字 |
| content | required、string、最大10,000文字 |

次の画面動作も必須です。

- 各入力欄の近くにエラーメッセージを表示する
- エラー項目を視覚的に判別できる
- バリデーション失敗後も入力内容を保持する
- 送信中は多重送信を防止する
- 正常時と異常時を利用者が区別できる

## 10. セキュリティ要件

### 10.1 XSS対策

投稿本文はプレーンテキスト仕様です。HTML入力やリッチテキスト編集は必須ではありません。

- 投稿本文をHTMLとして解釈しない
- `dangerouslySetInnerHTML`を使用しない
- `script`タグやイベント属性を含む文字列を保存してもJavaScriptが実行されない
- 攻撃文字列がレイアウトや他の利用者の画面を変更しない

改行表示にはCSSなどを利用し、HTMLを無加工で描画しないでください。

独自にリッチテキスト機能を追加する場合は、許可するタグと属性を限定したサニタイズ、自動テスト、採用理由の説明が追加で必要です。

### 10.2 その他

- 状態を変更するリクエストでCSRF保護を維持する
- `user_id`など認可に関係する値をクライアント入力から信用しない
- ユーザー入力を文字列連結したRaw SQLへ埋め込まない
- Mass Assignmentの対象を必要な項目に限定する
- パスワード、二段階認証の秘密情報、実在する認証情報をログへ出さない
- `.env`、秘密鍵、トークンをGitへ登録しない
- 認証・二段階認証に関するFortify標準の保護を理由なく無効化しない

## 11. React・Inertia.js要件

- ReactコンポーネントはTypeScriptで作成する
- Inertia.jsを利用してLaravelのControllerから画面へ必要なデータだけを渡す
- 認証ユーザー情報に秘密情報を含めない
- フォームの送信中、成功、失敗状態を適切に表示する
- バリデーションエラーを各入力欄へ関連付ける
- デスクトップとスマートフォンの両方で主要操作を行える
- フォーム部品にlabelを関連付け、キーボードでも操作できる
- ブラウザコンソールに未処理のJavaScriptエラーを出さない
- `npm run build`がエラーなく成功し、ビルドエラーを握りつぶさない

スターターキットの画面をそのまま残すだけでなく、ブログ機能と一貫したナビゲーションおよび画面遷移にしてください。ただし、装飾量そのものは採点の中心ではありません。

## 12. 自動テスト要件

PestまたはPHPUnitのどちらを使用しても構いません。`php artisan test`で全テストを一括実行できるようにしてください。

テストは外部サービスや開発用データに依存させず、テスト用データベースを使用してください。必要に応じてFactoryと`RefreshDatabase`を使用してください。

最低限、次のケースを自動テストしてください。

### 12.1 認証

- ユーザー登録に成功する
- 正しい認証情報でログインできる
- 誤ったパスワードではログインできない
- ログアウトできる
- 未ログインでは認証必須画面を利用できない

### 12.2 二段階認証

- 二段階認証を有効化し、正しいコードで確認できる
- 確認前は二段階認証が有効扱いにならない
- 二段階認証有効ユーザーはログイン時にチャレンジが必要になる
- 正しいTOTPコードでログインを完了できる
- 誤ったTOTPコードではログインできない
- 未使用のリカバリーコードでログインできる
- 使用済みリカバリーコードを再利用できない
- 二段階認証を無効化できる

### 12.3 投稿と認可

- 投稿一覧、詳細、作成、編集画面を表示できる
- ログインユーザーが投稿を作成できる
- 作成した投稿がログインユーザーに関連付く
- 投稿者本人が更新・削除できる
- 別ユーザーの更新・削除は`403`になる
- 認可失敗後もデータが変更されない

### 12.4 バリデーションとセキュリティ

- タイトルと本文が空の場合に保存できない
- タイトルが255文字を超える場合に保存できない
- 本文が10,000文字を超える場合に保存できない
- バリデーション失敗時に入力内容を復元できる
- 危険なHTML文字列を投稿しても、実行可能なHTMLとして描画されない

フィルター指定した一部のテストだけでなく、必ず全テストを実行してください。

## 13. Docker要件

採点者はWSL2またはLinux上で、Git、Docker、Docker Compose以外をホストへ追加せずに構築します。

- Docker Compose v2で起動できる
- 受験者自身が作成・管理する`Dockerfile`と`compose.yaml`をリポジトリへ含める
- アプリケーション、PHP、Webサーバー、MySQL、フロントエンドビルドに必要な構成をリポジトリへ含める
- クリーンなcloneと空のDockerボリュームから構築できる
- PHP、Composer、Node.jsの実際のバージョンをREADMEへ記載する
- ホスト側のポートは環境変数で変更できる
- 固定`container_name`を使用しない
- MySQLのホスト公開が不要なら公開しない
- MySQLの起動完了を考慮する
- MigrationとSeederを手順化する
- `npm run build`による本番ビルドをコンテナ環境で実行できる
- アプリケーションとテストが、開発者個人のファイルや既存ボリュームへ依存しない

Laravel Sailは使用せず、`Dockerfile`と`compose.yaml`を用いた独自のDocker Compose構成を作成してください。PHP、Composer、Node.js、MySQLを利用する処理はコンテナ内で完結させ、第三者がREADMEだけで再現できることを完了条件とします。

## 14. README要件

提出リポジトリのREADMEには、最低限、次の内容を記載してください。

- アプリケーション概要
- 使用技術と実際のバージョン
- 前提条件
- clone直後からのセットアップ手順
- 起動、停止、再構築、初期化のコマンド
- Migration、Seeder、フロントエンドビルドのコマンド
- アクセスURLとポート変更方法
- テスト実行方法
- テスト用ユーザーを用意する場合の認証情報
- 二段階認証を手動確認する手順
- 主要なURL設計
- UserとPostの関係が分かるER図または説明
- 認証、認可、XSS対策について採用した方針
- 既知の問題や未実装項目

READMEと実装の挙動を一致させてください。

## 15. Git・リポジトリ要件

### 15.1 Git管理対象

- `composer.lock`を登録する
- `package-lock.json`を登録する
- `.env.example`を登録する
- `.env`を登録しない
- `vendor`を登録しない
- `node_modules`を登録しない
- ログ、キャッシュ、セッション、ビルド途中の一時ファイルを登録しない
- OSやエディタ固有の不要ファイルを登録しない
- 提出時の作業ツリーを整理する

### 15.2 コミットメッセージ

コミットメッセージは、次の形式にしてください。

`{prefix}: {修正内容}`

修正内容は日本語で、何を変更したか分かるように記載してください。

主なprefixは次のとおりです。

| prefix | 用途 |
| --- | --- |
| `feat` | 機能追加 |
| `fix` | 不具合修正 |
| `test` | テストの追加・修正 |
| `refactor` | 挙動を変えないコード改善 |
| `docs` | READMEなどの文書変更 |
| `build` | Dockerやビルド構成の変更 |
| `chore` | その他の環境整備 |

例：

- `feat: 投稿の作成・編集・削除機能を実装`
- `fix: 他ユーザーの投稿を更新できる問題を修正`
- `test: 二段階認証のFeature Testを追加`
- `docs: Dockerのセットアップ手順を追加`

1つのコミットには、原則として1つの目的に関する変更を含めてください。`修正`、`update`、`作業完了`など、変更内容を判断できないメッセージは使用しないでください。GitHubが自動生成するマージコミットのメッセージは、この形式の対象外です。

### 15.3 ブランチとPull Request

提出リポジトリの既定ブランチは`main`とし、`main`へ直接実装をコミットしないでください。最新の`main`から、主要な作業単位ごとにブランチを作成します。

ブランチ名の例：

- `feature/authentication`
- `feature/posts`
- `feature/two-factor-authentication`
- `build/docker`
- `test/post-authorization`
- `fix/post-authorization`
- `docs/readme`

次の流れで開発してください。

1. 最新の`main`から作業ブランチを作成する
2. 実装内容が分かる単位でコミットする
3. 作業ブランチをGitHubへpushする
4. `main`に対するPull Requestを作成する
5. Pull Requestへ変更内容とテスト結果を記載する
6. 差分とテスト結果を確認してから`main`へマージする

認証、二段階認証、投稿CRUD、Docker、テストなどの主要な作業単位でブランチを分けてください。文言修正などの軽微な変更ごとに新しいブランチを作る必要はなく、関連する作業ブランチへまとめて構いません。

`main`は、原則としてビルドと全テストが成功する状態を維持してください。`main`へのforce pushや、共有済みコミットの履歴改変は行わないでください。提出時は、すべての必須機能をマージした`main`のコミットハッシュを共有してください。

## 16. 提出物

次の内容を提出してください。

- GitHubリポジトリURL
- 採点対象のブランチ名
- 採点対象のコミットハッシュ
- README
- LaravelおよびReactのソースコード
- Docker関連ファイル
- Migration、Factory、Seeder
- 全テストコード
- 実行結果

実行結果には、最低限、次の成功が分かるログを含めてください。

- Dockerイメージのクリーンビルド
- コンテナ起動
- Laravel 13.xおよびPHP 8.3以上の確認
- MigrationとSeeder
- フロントエンドの本番ビルド
- `php artisan test`による全テスト
- `composer audit`
- `npm audit`
- ブラウザコンソールに未処理エラーがないこと

スクリーンショットだけを提出して、再現手順やテストコードを省略することはできません。

## 17. 提出前チェック

提出前に、既存の開発用コンテナとボリュームに依存しない状態で、次を確認してください。

1. 新しいディレクトリへリポジトリをcloneする
2. READMEの手順だけでDocker環境を構築する
3. MigrationとSeederを実行する
4. フロントエンドをビルドする
5. 全テストを実行する
6. ユーザー登録から二段階認証ログインまでブラウザで確認する
7. 2人のユーザーを作り、他人の投稿を編集・削除できないことを確認する
8. 危険なHTML文字列を投稿し、JavaScriptが実行されないことを確認する
9. デスクトップとスマートフォン相当の画面幅で主要操作を確認する
10. READMEと実際のコマンド・遷移先が一致することを確認する

## 18. 必須範囲外

次の機能は本課題の必須範囲ではありません。

- コメント
- いいね
- タグ、カテゴリー
- 画像アップロード
- 管理者画面、権限ロール
- SNSログイン
- SMS認証
- WorkOS AuthKit
- メールアドレス確認
- パスワード再設定メール
- リッチテキストエディター
- 本番環境へのデプロイ

必須要件を満たした後に追加しても構いませんが、追加機能によって必須機能、セキュリティ、テスト、再現性を損なわないでください。

## 19. 質問・不具合報告

質問すること自体は問題ありません。質問時は、可能な範囲で次を整理してください。

- 実現したいこと
- 期待した結果
- 実際の結果
- 再現手順
- エラーメッセージまたはログ
- 確認したファイルとコード
- 既に試したこと
- 自分で切り分けた結果
- 判断できずにいる点

「動きませんでした」だけではなく、どこまで確認でき、何が未解決なのかを共有してください。
